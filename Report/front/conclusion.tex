\section{Conclusion}
\label{sec:conclusion}

\paragraph{Lessons from model building and evaluation.}
\begin{itemize}[leftmargin=*,itemsep=3pt]
\item \textbf{Check the structure of the columns before choosing a model.} Exact identities (Tasks 1 and 3), a latent two-by-two structure (Task 2), empty gaps (Task 5) and near-duplicate scenes (Task 4) gave more than model tuning. In several tasks the tuned models were at a ceiling set by the data's own noise.
\item \textbf{Optimise the decision rule of the metric, not the loss.} A threshold near 60\% flagged for binary F2 (a leaderboard probe gained $+0.0128$ over the macro-F2 cut), the conditional quantile $q=1-1/(2p)$ for NMAE, a fixed-point affine rule for macro F1, and a 10\% break-even for F3. Each is a few lines of code and worth more than another model in the blend.
\item \textbf{Out-of-fold scores can mislead under distribution shift.} In Task 4 the random-fold score reached 0.99 while the public test was harder: random folds contain near-duplicate scenes, so they measure memorisation. Scene-grouped folds ranked models better, although even they did not predict every leaderboard result (kNN smoothing improved the grouped score and lost on the public test).
\item \textbf{Isolate one change per probe.} Because the score averages five tasks, a change in one task is small and noisy. One-change probes, with the expected effect written down beforehand, separated real gains from luck, and showed that most late tuning (blend weights, seeds, thresholds) was below the leaderboard's resolution.
\item \textbf{Compliance is part of the method.} Two identifier leaks, a test-rank threshold and a test-prediction prior correction all helped the public score or would have, and we removed or did not use them after the TA's rulings. The compliant pipeline scores slightly lower on the leaderboard and is the one we can defend.
\end{itemize}

\paragraph{Machine learning in the game industry.} The five tasks show that a game platform produces cheap, plentiful, mostly tabular data in which the useful signal is often in the structure of missing values, ratios and joint ranges rather than in a large model. Decisions are asymmetric: a missed cheater or account takeover costs far more than a review, so F2 and F3, and explicit thresholds, are the business interface. \paragraph{Feeding a player-lifetime-value system.} The five outputs fit together as inputs to one player-lifetime-value (LTV) model, which we did not build. T3 gives the expected monthly spend and its uncertainty, and is the base of the LTV. T2 supplies the segment, which sets the horizon and the retention action. T1 and T5 enter as risk: a flagged cheater or a likely hijacked account lowers expected future value and triggers review or protection, so the LTV is discounted by the probability of a ban or a takeover. T4 supplies which game the player engages with, which lets the platform route support and tailor offers by title. In such a system the models must be scored and monitored together, because the same player can appear in several of them, and a shift in one task (new content in T4, a new cheat method in T1) should raise a flag before it reaches the revenue number.

Model outputs are useful only when the operations team can understand them (which rule fired, which segment, which game), and any model that scores players needs monitoring, because behaviour, content and cheating methods drift. Image models face a shifting content stream (new maps, new seasons), which is why Task 4 needed validation by scene rather than by image.

\paragraph{Future improvements.}
\begin{itemize}[leftmargin=*,itemsep=2pt]
\item \textbf{Validation.} Select thresholds and blend weights inside nested cross-validation or on a separate holdout (Task 1), and evaluate Task 4 on a held-out set of scenes that is unseen by construction, so that the model choice does not rely on the public leaderboard.
\item \textbf{Task 4.} More backbones no longer moved the public score. The next gains are more likely from the dark, low-confidence test images and from checking the train-prior adjustment on a set with a different class mix.
\item \textbf{Task 5.} Obtain labelled incidents from the security team, so the rules can be trained and scored, and use rolling windows to follow drift.
\item \textbf{Monitoring drift.} Track the share of flagged accounts (T1 and T5), the predicted class mix (T2 and T4) and the zero rate (T3) against their training values, and re-fit when they move.
\item \textbf{Inference cost.} The final Task 4 system uses a ViT-7B with adapters and several companion models and needs a large GPU. A production version should distil it into one smaller model and report time per image; the Task 1 to 3 pipelines already run on CPU in minutes.
\item \textbf{System level.} Connect the five predictions in an actual lifetime-value model and measure the effect of each task on that target.
\end{itemize}
